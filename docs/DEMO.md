# AI_LAWYER — демонстрация блока Contracts / Review

## Запуск

1. Скопируйте `.env.demo` → `.env`, заполните `TELEGRAM_BOT_TOKEN` и `OPENAI_API_KEY`.
2. Убедитесь, что каталог `rag/` с корпусом на месте (иначе RAG вернёт пусто).
3. Из корня репозитория:

```bash
# Windows CMD
set PYTHONPATH=%CD%
python -m app.bot.main
```

```powershell
$env:PYTHONPATH = (Get-Location).Path
python -m app.bot.main
```

## Три фиксированных демо-кейса

### Кейс 1 — Generate: поставка (short intake)

| Поле | Что вводить |
|------|-------------|
| Тип | Поставка / `4` |
| Название | `Договор поставки оборудования (демо)` |
| Стороны | Два ТОО с БИН и городами (коротко) |
| Тип поставки | `разовая` |
| Товар | `Сервер 2 шт., модель X, Алматы` |
| Сроки поставки | `30 дней с предоплаты` |
| Цена | `10 000 000 тенге с НДС` |
| Цена за единицу | `нет` |
| Оплата | `50% предоплата, 50% перед отгрузкой` |
| Сроки оплаты | `5 б/д с даты счёта` / остаток — по отгрузке |
| НДС | `с НДС` |
| Доп. условия | `нет` |
| Подтверждение | `подтвердить` |

**Ожидается:** превью текста + `contract.docx` + сообщение со списком норм из RAG.  
**Глазами:** шапка и стороны не «рыба», есть разделы о цене/оплате, один блок реквизитов в конце превью, без второго «ДОГОВОР» в середине.

---

### Кейс 2 — Generate: услуги (short intake)

| Поле | Что вводить |
|------|-------------|
| Тип | Услуги / `2` |
| Название | `Договор возмездного оказания услуг (демо)` |
| Стороны | Заказчик / Исполнитель с реквизитами |
| Вид услуг | `IT-сопровождение` |
| Предмет | `сопровождение сервера, 1 час реакции` |
| Срок | `12 месяцев с даты подписания` |
| Цена | `5 000 000 тенге, НДС включён в сумму` |
| Цена за единицу | `нет` |
| Оплата | `ежемесячно, до 10 числа` |
| Сроки оплаты | `5 б/д с даты счёта` |
| НДС | `с НДС` |
| Доп. | `нет` |
| | `подтвердить` |

**Ожидается:** как в кейсе 1 (превью, DOCX, нормы).  
**Глазами:** роли Исполнитель/Заказчик согласованы, § цена / оплата не смешаны в один абзац без смысла.

---

### Кейс 3 — Review (анализ договора)

1. Кнопка **«Анализ документа»** или `/analysis`
2. Тип: `договор поставки`
3. Вставить **короткий** фрагмент (самостоятельно или из превью после кейса 1) — 1–2 экрана текста с ценой, сроком, штрафом.
4. Цель анализа: `риски и что исправить перед подписанием`
5. Контекст: `проверка перед подписанием` или `нет`
6. **подтвердить**

**Ожидается:** несколько сообщений с разбором (HTML), затем отдельное сообщение со списком норм RAG.  
**Глазами:** есть секции вроде «Общая оценка», «Ключевые риски», «Практический вывод»; нет бесконечного «реферата»; мало дословных повторов подряд.

## Smoke checklist перед показом

### Generate
- [ ] Договор доходит до конца без ошибки
- [ ] Факты из опроса видны в тексте (не вся рыба)
- [ ] Уходит файл `contract.docx`
- [ ] После превью приходит блок норм (RAG)
- [ ] Нет дубля финальных реквизитов / двух шапок (быстрый просмотр)

### Review
- [ ] Анализ укладывается в ожидаемую структуру (заголовки разделов)
- [ ] Второе сообщение — нормы
- [ ] Текст не выглядит как один сплошной лекционный реферат

### Telegram / UX
- [ ] Все кнопки главного меню открывают свои сценарии
- [ ] После «Договор» можно перейти, например, в «Претензию» без тишины
- [ ] DOCX открывается у вас локально тестом
- [ ] При ошибке пользователь видит **понятный** текст, а не только технический дамп

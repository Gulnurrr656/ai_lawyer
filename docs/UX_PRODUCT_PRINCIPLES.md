# Продуктовые принципы UX (канон)

Документ фиксирует обязательную модель опыта для юридического Telegram-бота. Изменения в сценарных потоках, промптах и gate/repair должны с ним согласовываться.

## 1. Ветвление только там, где это юридически значимо для изоляции сценария

В **начале** сценария допускается только **минимально необходимое** ветвление, например:

- А / Б (и аналоги заявлений);
- жалоба / претензия;
- тип договора;
- маршрут банкротства (ФЛ / ИП / ТОО);

и другие развилки **только если** без них нельзя корректно зафиксировать `scenario_id`, жанр, retrieval и последующую генерацию.

Лишние формальные развилки «чтобы было как в шаблоне» не вводятся.

## 2. После выбора ветки — максимально свободный ввод

После фиксации ветки пользователь может:

- писать обычным языком, кратко или сумбурно;
- пропускать детали;
- пользоваться **голосом** (где подключён dispatch);
- не использовать юридическую терминологию;
- не знать, как оформляется документ.

Требование «ответить ровно по полям шаблона» на этом этапе не является нормой.

## 3. Система не требует от пользователя юридически «правильной» структуры

Система **сама**:

- интерпретирует намерение и контекст ветки;
- извлекает факты из свободного текста;
- определяет пробелы;
- достраивает юридическую форму и аргументацию;
- вместо жёсткого отказа по нехватке данных использует маркеры **`[УТОЧНИТЬ: …]`** с указанием, что именно желательно уточнить у клиента;
- опирается на **RAG** как на единственную каноническую правовую основу для норм в ответе;
- стремится к **лучшему возможному результату** в рамках жанра и имеющихся данных.

Gate и repair работают как **страховка жанра и качества**, а не как «экзамен» для пользователя.

## 4. Клиент не обязан писать как юрист

Ожидаемое поведение:

> Клиент пишет как человек.  
> Бот понимает и структурирует как юрист.  
> Бот оформляет сильный профессиональный результат.

Не допускается проектировать шаги так, будто пользователь обязан знать процессуальный шаблон, термины или полный состав реквизитов до первой выдачи.

## 5. Инварианты архитектуры (не ослабляются «ради простоты»)

Параллельно с мягким UX сохраняются:

- **scenario lock** (`scenario_id` / `_fsm_active_scenario` / feature);
- **feature isolation** (пайплайны не смешивают консультацию, иск, претензию и т.д. после выбора ветки);
- **RAG-first** (нормы в аргументации — из библиотеки, без выдуманных статей);
- **жанровая дисциплина** (консультация ≠ договор ≠ иск; пост-LLM gate по жанру остаётся, но не подменяет собой требования к «идеальному вводу» пользователя).

Принцип: **вход мягкий, внутри строго, выход сильный и по жанру.**

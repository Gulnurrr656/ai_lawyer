# Ручная test matrix (Telegram)

Продуктовые ожидания по свободному вводу и ветвлению: **`docs/UX_PRODUCT_PRINCIPLES.md`**.

Инструкция: отметить **Pass / Fail** после прогона в боевом боте.

## Порядок проверки в первую очередь (реальный UX)

Цель: поймать сброс состояния, confirm и смешение сценариев до долгих маршрутов.

| Приоритет | ID | Зачем |
|-----------|-----|--------|
| 1 | G1 | `/start` после любого незавершённого шага — меню, нет «зависшего» ответа от старого FSM |
| 2 | X1 | Середина сценария A → `/start` → вход в сценарий B с первого шага |
| 3 | X2 | Середина сценария → отмена (слова из cancel-config) → другой сценарий |
| 4 | G3 | Голос на одном шаге + текст на другом (тот же сценарий) |
| 5 | Q1, A1 | Confirm → выдача; при fail verify — не более одного осмысленного repair (консультация / анализ) |
| 6 | P1 или P2, K1 или K2 | Один документо-ориентированный happy-path |
| 7 | B1 | Короткий проход банкротства ФЛ до выдачи текста |
| 8 | C1 | Один профиль договора (договорной роутер последний в `main.py` — не ломать порядок) |

Широкий полный охват (C2–C5, B2–B4) — после того как приоритет 1–5 стабилен.

## Перед прогоном (авто)

Из корня репозитория одной командой:

```text
python scripts/pre_telegram_e2e.py
```

Ожидаемый вывод: `pre_telegram_e2e: ok` (внутри: `compileall` + `smoke_scenario_quality`).

Либо вручную:

1. `python -m compileall -q app`
2. `python scripts/smoke_scenario_quality.py` — импорты и минимальные вызовы `scenario_quality_dispatch` (должно напечатать `smoke_scenario_quality: ok`).

Канон качества пост-LLM: `ScenarioDefinition` → `app/shared/scenario_quality_dispatch.py` (`run_post_llm_verify`, `max_repair_rounds_for_scenario`, `build_repair_user_prompt`). Сценарии **consult** и **analyze** ходят в dispatch из пайплайнов; прочие пайплайны могут подключаться позже без смены верификаторов.

Переменные окружения (опционально):

| Переменная | Эффект |
|------------|--------|
| `SCENARIO_QUALITY_MAX_REPAIR__consult_memo` | Верхняя граница repair-раундов для профиля (0–3), иначе дефолт из dispatch |
| `SCENARIO_QUALITY_MAX_REPAIR__analyze_document` | То же для анализа документа |
| `CONSULT_VERIFY_REPAIR_ROUNDS` | Если задана, перекрывает cap только в пайплайне консультации |
| `ANALYZE_VERIFY_REPAIR_ROUNDS` | Если задана, перекрывает cap только в пайплайне анализа |

Ожидаемое поведение **без сюрпризов**: один раунд repair при провале gate — только если верификатор не прошёл (длина / структура / жанр); при успешной первой генерации второй вызов LLM нет.

### Фокус стабилизации: G1, Q1, A1 (пошагово в Telegram)

Перед шагами в Telegram: `python scripts/pre_telegram_e2e.py`. Для Q1/A1 на бэкенде нужен уровень логов **INFO** (строки `consult quality …` / `analyze quality …`).

**G1 — чистый вход**

1. Запустить бота, отправить `/start`.
2. Убедиться: ответ с меню/клавиатурой, без ошибки.
3. (Доп.) Начать любой сценарий, не заканчивая → снова `/start` → снова меню; следующий сценарий должен открываться **с первого шага**.

**Q1 — консультация**

1. Меню «Консультация» → пройти опрос до сводки → **подтвердить** тем же лексиконом, что в матрице (см. confirm).
2. Ожидание: один проход LLM; если gate не прошёл — не более одного repair (см. логи сервера: `consult quality gate`, `consult quality repair`).
3. Зафиксировать: объём, наличие блоков по смыслу 1–6, отсутствие «хвоста договора/иска».

**A1 — анализ документа**

1. Меню анализа → тип → вставить **короткий** тестовый текст договора (или небольшой DOCX/PDF с текстовым слоем) → цели → контекст → **подтвердить**.
2. Ожидание: пять заголовков `###` в ответе в порядке из промпта; после «Практический вывод» нет новых `###`.
3. Логи: `analyze quality gate`, `analyze quality repair` — repair только при `ok=false` на первом проходе.

| ID | Gate слишком строгий (что именно) | Лишний repair (без видимой проблемы текста) | Ответ заметно сильнее | Ложный fail (текст норм, gate ругнулся) | Примечание |
|----|-----------------------------------|---------------------------------------------|------------------------|------------------------------------------|------------|
| Q1 | | | | | |
| A1 | | | | | |
| G1 | — | — | | | только UX сброса |

По итогам: если паттерн **повторяется** (одна и та же причина fail / лишний repair) — зафиксировать текст в логе (`reason=`) и завести задачу на **узкую** правку верификатора или порога; расширять `scenario_quality_dispatch` на petitions/claims/bankruptcy/contracts — только если польза подтверждена несколькими прогонами.

## Переключение сценариев и сброс

| ID | Проверка | Ожидание | Результат |
|----|-----------|----------|-----------|
| X1 | Начать консультацию (или заявление) → 1–2 ответа → `/start` → сразу другой сценарий (напр. претензия) | Новый сценарий с чистого шага; нет ошибки pipeline «другой сценарий» без входа из меню | |
| X2 | Середина опроса → фраза отмены из `app/shared/config/cancel.py` (`CANCEL_WORDS`) → другой сценарий | `state.clear`, приветствие отмены, вход с первого шага | |
| X3 | После успешной выдачи (любой сценарий) → `/start` → тот же сценарий снова | Поведение как при первом входе | |

Слова подтверждения на шагах **confirm** в сценариях согласованы с голосовым подтверждением транскрипта (`подтвердить`, `да`, `ок`, …). Неверное слово на confirm → бот просит повторить, **без** вызова pipeline.

## Голос: где подключён dispatch

Голос обрабатывается **только** если для текущего `FSM state` есть обработчик в `app/shared/voice_dispatch.py` (в т.ч. контракт через внутренний ключ потока). Если бот отвечает «на этом шаге голос не подключён» — для E2E этот шаг пройти **текстом**; для проверки G3 возьмите шаг из таблицы dispatch (например `ConsultStates.topic`, `ClaimsStates.confirm`, шаги банкротства до `confirm_intake`).
